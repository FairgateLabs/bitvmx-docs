    Union Bridge Technical Documentation¶

    Union Bridge is a trust-minimized bridge protocol for BTC transfers between Bitcoin and Rootstock, implemented using BitVMX's multi-party optimistic proving system.

    System Architecture¶

    Core Components¶

    BitVMX Verification Layer - Multi-party optimistic proving system operating on Bitcoin - Fraud-proof verification mechanism - RISC-V virtual machine for computation verification - Hash chain commitments for state tracking

    Bitcoin Layer - Taproot scripts for complex transaction logic - Time-locked contracts for challenge periods - Packet-based transaction batching - SPV (Simplified Payment Verification) proofs

    Rootstock Layer - Bridge smart contracts for token minting/burning - Light client for Bitcoin header verification - Event emission system for cross-chain communication

    Operator Network - Permissionless functionary participation - Collateral staking and slashing mechanisms - Event monitoring and relay services - Challenge submission system

    Packet-Based Architecture¶

    Union Bridge uses a packet system that groups multiple bridge operations together:

    • Capital Efficiency: Security bonds are reused across operations within a packet
    • Cost Amortization: Bitcoin transaction fees spread across multiple transfers
    • Batched Processing: Multiple peg-outs handled in single Bitcoin transaction sequence

    Benefits: - Reduces per-operation costs - Improves operator capital utilization - Increases system throughput

    Enabler System¶

    The enabler manages functionary participation:

    Registration: Operators stake collateral to participate in bridge operations

    Penalty Enforcement: Slashing mechanism for malicious behavior

    Reward Distribution: Honest operators receive fees for processing operations

    Exit Mechanism: Time-locked withdrawal for operator collateral

    Stopwatch Timelock Optimization¶

    Union Bridge implements an optimized time-lock mechanism:

    • Challenge period begins when assertion is made
    • Pauses during active disputes
    • Resumes after dispute resolution
    • Expires to release funds if no valid challenge

    This balances security (adequate time for fraud detection) with efficiency (minimal delay for honest operations).

    Security Model¶

    1-of-N Honest Assumption¶

    Union Bridge operates under the assumption that at least one participant remains honest. This differs fundamentally from federated bridges requiring honest majorities.

    Security Guarantee: The bridge remains secure if any single honest operator exists to challenge fraudulent operations.

    Comparison with Alternatives:

    Bridge Type Security Assumption Attack Threshold
    Federated (m-of-n multisig) Honest majority m+ colluding parties
    Committee-based ⅔+ honest ⅓+ colluding parties
    Union Bridge (1-of-n) Any one honest n-1 colluding parties

    Economic Security¶

    Operators stake collateral that can be slashed for malicious behavior:

    Attack Cost > Collateral at Risk + Opportunity Cost
Attack Profit = 0 (fraud is blocked)

    Rational actors have no economic incentive to attempt fraud.

    Fraud Proof System¶

    When fraudulent operations are detected:

    1. Honest operator submits challenge transaction
    2. BitVMX executes fraud proof on-chain
    3. Bitcoin Script verifies the proof deterministically
    4. Malicious operator's collateral is slashed
    5. Challenger receives reward from slashed funds

    Protocol Operations¶

    Peg-In (Bitcoin → Rootstock)¶

    Phase 1: Bitcoin Deposit 1. User sends BTC to Taproot peg-in address 2. Transaction confirms on Bitcoin (typically 6 confirmations) 3. SPV proof is constructed

    Phase 2: Proof Relay 1. Operator monitors Bitcoin for deposits 2. Constructs inclusion proof with block header 3. Submits proof to Rootstock bridge contract

    Phase 3: Token Minting 1. Bridge contract verifies SPV proof 2. Confirms Bitcoin finality 3. Mints wrapped BTC to user's Rootstock address

    Security: Relies on Bitcoin's proof-of-work consensus. No trust in operators required—anyone can relay valid proofs.

    Peg-Out (Rootstock → Bitcoin)¶

    Phase 1: Token Burning 1. User calls burn function on bridge contract 2. Contract records burn event with destination address 3. Event is emitted for operator monitoring

    Phase 2: Packet Creation 1. Operator collects multiple burn events 2. Groups them into a packet for efficiency 3. Constructs Bitcoin transaction sequence

    Phase 3: Bitcoin Submission 1. Kickoff transaction initiates the peg-out on Bitcoin 2. Operator locks collateral 3. Assert transaction claims validity of burns

    Phase 4: Challenge Period - Duration: Configurable based on packet value (hours to days) - Purpose: Allow honest operators to detect and challenge fraud - Outcome: Proceed to unlock if no valid challenge

    Phase 5: Finalization - If no challenge: Unlock transaction releases BTC to recipients - If challenged: Fraud proof executed, fraudulent packet rejected

    Security: 1-of-n assumption guarantees at least one operator will challenge invalid packets.

    Light Client Framework¶

    Union Bridge implements a flexible light client system adaptable to different blockchain architectures:

    Bitcoin Light Client on Rootstock¶

    • Verifies Bitcoin block headers
    • Validates proof-of-work
    • Confirms transaction inclusion via Merkle proofs
    • Tracks longest chain for finality

    Rootstock State Verification on Bitcoin¶

    • Zero-knowledge proofs for block validation
    • Transaction existence proofs
    • State commitment verification
    • Event log inclusion proofs

    Adaptability¶

    The light client framework is designed to support various blockchain architectures beyond Rootstock, enabling Union Bridge to be deployed for other chains.

    Transaction Structure¶

    Kickoff Transaction¶

    Inputs: Operator's funding inputs
Outputs:
  - Connector output (spent by subsequent tx)
  - Challenge output (allows disputes)
  - Fee output

    Assert Transaction¶

    Inputs: Kickoff connector output
Outputs:
  - Assertion commitment
  - Timelock output (challenge period)

    Challenge Transaction¶

    Inputs: Challenge output from kickoff
Outputs:
  - Fraud proof data
  - Dispute resolution outputs

    Unlock Transaction¶

    Inputs: Assert timelock output (after challenge period)
Outputs:
  - BTC to user addresses (from packet)
  - Operator collateral return

    Zero-Knowledge Proofs¶

    Union Bridge uses ZK proofs for efficient verification:

    Block Validity: Proves Rootstock blocks follow consensus rules

    Transaction Inclusion: Proves specific transaction exists in block

    State Transition: Proves contract state changes correctly

    Event Emission: Proves event log entry exists

    ZK proofs enable compact verification of complex computations on Bitcoin.

    API Integration¶

    Monitoring Peg-Ins¶

    Operators monitor Bitcoin for deposits:

    GET /bitcoin/blocks/latest
GET /bitcoin/tx/{txid}/confirmations
POST /rootstock/bridge/relay-proof

    Processing Peg-Outs¶

    Operators monitor Rootstock for burns:

    GET /rootstock/events?type=burn
GET /rootstock/bridge/pending-packets
POST /bitcoin/submit-packet

    Challenge Submission¶

    Monitoring for fraud:

    GET /bitcoin/packets/active
POST /bitcoin/challenge
POST /bitcoin/fraud-proof

    For complete API specifications, see the API Reference section.

    Implementation Considerations¶

    Operator Requirements¶

    Infrastructure: - Bitcoin full node (archival or pruned with relevant blocks) - Rootstock full node - Monitoring service for both chains - Key management for signing transactions

    Collateral: - Sufficient BTC to cover packet value - Additional margin for Bitcoin fees - Staking period commitment

    Network Connectivity: - Reliable connection to both networks - Low latency for timely challenge submission

    Gas Costs¶

    Bitcoin: - Kickoff tx: ~500 vBytes - Assert tx: ~300 vBytes - Unlock tx: ~200 vBytes + user outputs - Challenge tx: Variable based on fraud proof complexity

    Rootstock: - Proof relay: ~100k gas - Token minting: ~50k gas - Token burning: ~30k gas

    Challenge Period Configuration¶

    Recommended challenge periods based on packet value:

    Packet Value Challenge Period Security Reasoning
    < 1 BTC 12 hours Lower risk, faster finality
    1-10 BTC 24 hours Balanced risk/speed
    10-100 BTC 48 hours Higher risk, need detection time
    > 100 BTC 72+ hours Maximum security

    Testing and Deployment¶

    Testnet Deployment¶

    Union Bridge is deployed on Bitcoin testnet and Rootstock testnet:

    • Test peg-in/peg-out flows
    • Simulate challenge scenarios
    • Measure gas costs and timing
    • Verify fraud proof execution

    Mainnet Deployment¶

    Production deployment on Bitcoin mainnet and Rootstock mainnet includes:

    • Multi-sig governance for upgrades (temporary, transitioning to immutability)
    • Monitored operator set
    • Graduated value limits during initial phase
    • Circuit breakers for anomalous activity
